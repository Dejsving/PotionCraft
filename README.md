## 1. СУТЬ ПРОЕКТА

PotionCraft — это **веб-инструмент общего стола** для автоматизации homebrew-механик «Гербализм и Алхимия» к D&D 5e. Он **не является** одиночным приложением для одного игрока — в него одновременно играют несколько участников одной сессии с разных вкладок браузера. Мастер подземелий (DM) и игроки используют один и тот же URL.

**Ключевая цель:** снять рутину бросков кубиков, ведения инвентаря трав и расчётов при варке зелий прямо на живой игровой сессии — инструмент должен работать быстро и не прерывать нарратив.

## 2. АРХИТЕКТУРНАЯ МОДЕЛЬ

### 2.1 Многопользовательский SSR без авторизации

- Приложение работает как **Server-Side Rendered** инструмент.
- **Авторизации нет вообще.** Нет логинов, нет учётных записей.
- Каждый участник стола при первом открытии получает **`player_session_id`** — генерируется на клиенте и хранится в **`sessionStorage`** (не localStorage). При закрытии вкладки — сессия исчезает.
- Персонажи **резервируются** под конкретный `player_session_id`. Если персонаж уже занят другой сессией — сервер возвращает **HTTP 409 Conflict**.
- Игровое состояние живёт только в рамках одной браузерной сессии; перезагрузка вкладки или закрытие = новая эфемерная сессия.

### 2.2 Структура репозитория (.NET Solution)

```
PotionCraft/
├── PotionCraft.Client/         # UI-слой: HTML, CSS, JS (ванильный фронтенд)
├── PotionCraft.Contracts/      # Слой контрактов: DTO, интерфейсы, доменные модели
├── PotionCraft.InitData/       # Seeding: все данные из источника правил (травы, таблицы биомов, рецепты)
├── PotionCraft.Repository/     # Паттерн Repository: доступ к данным
├── PotionCraft.Server/         # Основной ASP.NET-проект: контроллеры, сервисы, middleware
├── PotionCraft.Tests/          # Unit- и интеграционные тесты
├── deploy/                     # Конфигурации деплоя
├── .github/                    # CI/CD (Actions)
└── PotionCraft.sln
```

### 2.3 Технологический стек

| Слой | Технология |
|---|---|
| Backend | C# (.NET), ASP.NET |
| Frontend | HTML, CSS, JavaScript (без фреймворков) |
| Хранение данных | In-memory / seed-файлы (БД не используется как persistent storage) |
| Сессии | `sessionStorage` на клиенте, сервер валидирует `player_session_id` |
| Деплой | Docker / конфигурация в `/deploy` |
| CI | GitHub Actions |

## 3. ДОМЕННАЯ МОДЕЛЬ (ENTITIES)

### 3.1 Персонаж (Character)

Атрибуты:
- Имя
- Модификатор Гербализма = мак(МДР, ИНТ) + профбонус (если есть набор гербалиста)
- Модификатор Алхимии = мак(ИНТ, МДР) + профбонус (если есть алхимический набор)
- Инвентарь трав (сумка)
- Инвентарь зелий/ядов (сумка)
- `player_session_id` — какая сессия владеет персонажем в данный момент

**Резервирование персонажа:** при попытке занять уже занятого персонажа → HTTP 409.

### 3.2 Ингредиент (Ingredient)

Атрибуты:
- `name` — Название
- `rarity` — Редкость: Обычный / Необычный / Редкий / Очень редкий / Легендарный
- `type` — Тип:
  - `PotionEffect` (Эффект зелья — база)
  - `PotionModifier` (Модификатор зелья)
  - `PoisonEffect` (Эффект яда — база)
  - `PoisonModifier` (Модификатор токсина)
  - `Magic` (Магический)
  - `Special` — особые ингредиенты, имеющие несколько применений (например, Хромовая слизь работает как Мод. Зелья И Мод. Токсина; Рвоск аналогично)
- `difficultyModifier` — Модификатор сложности (знаковое целое, от -2 до +5)
- `effect` — Текстовое описание эффекта
- `biomes` — Список биомов, в которых встречается
- `isElementalWater` — bool, только для Элементальной воды

### 3.4 Зелье / Яд (Potion / Poison)

**Обычное зелье:**
- Ровно 1 ингредиент с типом `PotionEffect` (база)
- От 0 до 3 ингредиентов с типом `PotionModifier` (модификаторы)
- СЛ варки = 10 + сумма всех модификаторов сложности

**Яд:**
- Ровно 1 ингредиент с типом `PoisonEffect` (в 99% случаев это Лепестки Змееуста, но Дыхание Василиска тоже имеет этот тип)
- От 0 до 3 ингредиентов с типом `PoisonModifier`
- СЛ варки = 10 + сумма всех модификаторов сложности

**Магическое зелье:**
- Ровно 1 Элементальная вода (база, `isElementalWater = true`)
- Ровно 1 ингредиент с типом `Magic`
- Модификаторы **запрещены** (добавление любого модификатора = волна дикой магии / порча)

## 4. БИЗНЕС-ПРАВИЛА И АЛГОРИТМЫ

### 4.1 Гербализм (сбор трав)

#### Базовый алгоритм

1. Игрок выбирает **биом** из 10 доступных.
2. Игрок указывает **параметры окружения** (влияют на модификаторы некоторых результатов):
   - Время суток: день / ночь
   - Погода: идёт дождь / нет
   - Точная локация: у воды / в пещере / на берегу / под водой
3. Система симулирует бросок **2к6** (нормальное распределение, результаты 2–12).
4. Результат сопоставляется с таблицей биома → определяется ингредиент.
5. Если ингредиент найден — количество определяется по таблице доп. правил (см. 4.1.2).
6. При успешной проверке Гербализма (СЛ 15) → результат подтверждается, игрок добывает **1к4 порций** найденного ингредиента.

#### Механизм «Элементальная вода» (скрытый бросок)

Срабатывает при основном броске 2к6 со значением **2, 3, 4** или **10, 11, 12** (крайние результаты).  
При этом условии:
1. Система делает **скрытый бросок 1к100** (игрок не видит результата).
2. Если результат **> 75** → найденный ингредиент **заменяется** на «Элементальную воду».
3. Вероятность замены: ~25% от всех крайних бросков (т.е. ~25% × (5/11) ≈ 11% от всех бросков вообще).

**Исключение:** результат 12 в Пустыне — Элементальная вода добавляется безусловно, без d100.

### 4.2 Алхимия (варка зелий) — в планах, не завершено

#### Расчёт СЛ варки (работает как превью)

```
СЛ = 10 + Σ(модификаторы сложности всех выбранных ингредиентов)
```

Пример: Корень дикого Шалфея (0) + Семена Молочая (+2) + Кисть Генгкоу (+2) → СЛ = 14.

#### Валидация рецепта (планируемое поведение)

**Текущее состояние:** три поля для модификаторов всегда показываются сразу (пустые по умолчанию); заполнять не обязательно. Валидация «не более 3 модификаторов» убирается, логика контролируется количеством полей.

**Целевые правила:**
- Обычное зелье/яд: 1 поле «Эффект» + до 3 полей «Модификатор».
- Магическое зелье: 1 поле «Элементальная вода» + 1 поле «Магический ингредиент», поля модификаторов **скрыты/заблокированы**.

#### Процесс варки (планируется)

1. Игрок выбирает ингредиенты (1 база + до 3 модификаторов).
2. Система показывает превью: СЛ варки, итоговый эффект.
3. Игрок нажимает «Варить».
4. Система симулирует бросок (мод. Алхимии персонажа vs. СЛ).
5. **Успех:** ингредиенты списываются из инвентаря, зелье добавляется в сумку.
6. **Провал:** ингредиенты всё равно расходуются (сгорают); зелье не создаётся или создаётся дефектным (на усмотрение DM — реализовать как флаг).

## 7. ОБНАРУЖЕННЫЕ БАГИ И РАСХОЖДЕНИЯ

### 7.1 Баги в данных (расхождения источника правил → InitData)

**BUG-01: Рвоск — разный модификатор сложности в двух таблицах**
- В таблице «Ингредиенты зелий»: Рвоск, СЛ мод. = **+1**
- В таблице «Ингредиентов ядов»: Рвоск, СЛ мод. = **+2**
- Это один и тот же ингредиент (`Special: PotionMod + PoisonMod`), но с двумя разными цифрами в источнике.
- Требует решения: либо хранить два отдельных модификатора (`difficultyAsPotion`, `difficultyAsPotion`), либо принять одно значение и задокументировать решение.

**BUG-02: Опечатка «Сетопыль шляпки» вместо «Светопыль шляпки» в таблицах биомов**
- Горы, результат 10: написано `Сетопыль шляпки` — должно быть `Светопыль шляпки`.
- Подземье, результат 10: та же ошибка.
- В таблице InitData нужно использовать правильное написание с привязкой к ID ингредиента, а не к тексту.

**BUG-03: Лепестки Змееуста помечены как «Мод. Токсина» вместо «Эффект яда»**
- В источнике правил в шапке таблицы у Лепестков Змееуста написано «Мод. Токсина», но по всей логике системы и явному описанию («базовый ингредиент для всех ядов») это `PoisonEffect`, а не `PoisonModifier`.
- Если реализовать как модификатор — яды невозможно создать (нет базового ингредиента).
- Решение: хранить как `PoisonEffect`.

**BUG-04: Особый результат в Пустыне (2к6 = 12) — безусловная Элементальная вода**
- В таблице Пустыни результат 12 = «Корень пустоты» + «Дополнительно находится 1 Элементальная вода».
- Это отличается от стандартного механизма скрытого d100: здесь Элементальная вода **добавляется сверху**, а не **заменяет** основной ингредиент.
- Риск: если генератор Элементальной воды реализован только через d100-замену, этот случай выпадет из логики.

**BUG-05: В Подземье нет результатов 6-8 через таблицу «Обычные»**
- Все остальные биомы при результате 6, 7, 8 указывают «Повсеместный ингредиент → таблица Обычные».
- В Подземье каждая строка 2–12 имеет свой уникальный ингредиент, нет ни одной ссылки на таблицу Обычные.
- Это не баг источника, а намеренная особенность биома — но нужно убедиться, что код это корректно обрабатывает (не пытается обратиться к таблице Обычных при броске 6 в Подземье).

### 7.2 Архитектурные / логические баги

**BUG-06: Серверная валидация «не более 3 модификаторов» отсутствует**
- Валидация только на клиенте — при прямых API-запросах (или через devtools) ограничение обходится.
- Статус: планируется убрать валидацию и заменить на UX-решение (всегда 3 фиксированных поля).
- До завершения этого изменения — сервер принимает некорректные рецепты.

**BUG-07: Нет защиты от одновременного выпадения Элементальной воды через d100 + специальное правило Пустыни**
- Если в Пустыне выпадает 2, 3, 4 (крайние числа, но не 12), d100 может заменить ингредиент на Элементальную воду.
- Результат 12 в Пустыне дополнительно выдаёт Элементальную воду безусловно.
- Возможна ситуация: результат 12 → Корень пустоты + Элементальная вода (безусловно) + d100 → ещё одна Элементальная вода. Нужно явно уточнить: применяется ли d100 к результату 12 в Пустыне.

**BUG-08: Кровьтрава в таблице «Обычные», результат 7 — неоднозначное правило**
- «Перебросить, если не используется как провизия» — неясно, кто принимает решение (DM или система автоматически) и как система должна это обрабатывать в автоматическом режиме.
- Риск: при автоматическом режиме сбора может происходить бесконечный перебросок или некорректная замена.

### 7.3 UX / данные

**BUG-09: README в репозитории содержит устаревшую информацию об идентификации ингредиентов**
- В README описана механика идентификации (Эпик 2), которая принята к удалению.
- Вводит в заблуждение новых разработчиков или ИИ-аналитиков, читающих README как Source of Truth.

## 8. ПРИНЦИПЫ ДЛЯ ГЕНЕРАЦИИ ЗАДАЧ

При постановке задач аналитику следует:

**Задачи данных (InitData):**
- Создать/проверить сид-файлы для всех трёх таблиц ингредиентов (зелья, яды, магические).
- Учесть BUG-01 (два значения СЛ для Рвоска) — принять решение и зафиксировать в задаче.
- Убедиться, что Лепестки Змееуста хранятся с типом `PoisonEffect`.
- Таблицы биомов хранить как структуры с полями: `roll` (int), `ingredientId` (ref), `quantity` (enum: Fixed/Random1to2/Conditional), `condition` (enum: null/Night/Rain/Cave/OnShore).

**Задачи сервиса Гербализма:**
- `HerbalismService.Gather(biome, environmentParams)` — принимает биом и параметры окружения, возвращает найденный ингредиент + количество.
- Отдельный метод `DiceService.Roll(diceType)` для 1к4, 2к6, 1к100.
- Логика Элементальной воды: проверить, крайний ли бросок → если да → скрытый d100 → замена или нет.
- Обработать исключение для Пустыни, результат 12 (безусловная Элементальная вода, добавляется сверху).

**Задачи сервиса Алхимии:**
- `AlchemyService.Preview(ingredients)` → СЛ + текст эффекта (реализовано частично).
- `AlchemyService.Brew(characterId, ingredients)` → бросок vs. СЛ, списание ингредиентов, создание зелья.
- Валидация типов: нельзя смешать `PotionEffect` и `PoisonEffect` в одном рецепте.
- Валидация магического рецепта: Элементальная вода + только `Magic`; модификаторы запрещены.

**Задачи UI:**
- Форма сбора: дропдаун биома + чекбоксы (Ночь? Дождь? В пещере? На берегу? Под водой?) + кнопка.
- Форма алхимии: 1 поле «Эффект» + 3 всегда видимых поля «Модификатор» (убрать валидацию на количество, заменить на UX).
- Магическая варка: показывать особую форму (Элементальная вода + 1 магический ингредиент), скрыть поля модификаторов.

**Задачи сессий:**
- Генерация `player_session_id` при первом открытии (`sessionStorage`).
- Передача `player_session_id` во всех запросах.
- Корректная обработка HTTP 409 при резервировании персонажа (показать пользователю сообщение).
- Освобождение персонажа при закрытии вкладки (`beforeunload`).
